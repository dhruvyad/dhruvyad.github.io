Where Tokens Per Second Comes From

"How many tokens per second?" is not one number. It is the answer to an optimisation problem whose constraints are a memory bus, a cache hierarchy, and how many strangers you are willing to make wait. Here is the whole calculation, worked out on a real 753-billion-parameter model.

Ask how fast a model runs and you will get a number with no units attached to it — no batch size, no context length, no hardware, no precision. That number is nearly meaningless, because throughput and latency in a language model trade against each other so sharply that the same weights on the same GPUs can serve 39 tokens per second per user or 947, depending on choices made by whoever configured the server.

This article derives that number from first principles. Rather than reason about a hypothetical model, I use GLM-5.2, Zhipu AI's 753B-parameter open-weights model — every architectural constant below comes from its published config.json, and the parameter accounting is checked against the actual size of its weight files. The 282 safetensors shards total 1,506,667,387,408 bytes. At two bytes per bf16 parameter that is 753.33B parameters, and the analytic budget in the table below reproduces it to within 0.006% — the residual is layernorm and bias vectors I did not bother counting. Choosing a model whose weights you can actually inspect matters, because the interesting parts of this calculation are all architecture-specific.

One equation, two regimes

Every inference performance question reduces to a single question: for one step of work, is the machine waiting on arithmetic or on memory? A step needs to read some number of bytes from memory and perform some number of floating-point operations, and those happen concurrently, so the step takes as long as the slower of the two:

t_{\text{step}} = \max\!\left(\underbrace{\frac{\text{bytes}}{\mathit{BW}}}_{\text{memory}},\; \underbrace{\frac{\text{FLOPs}}{C}}_{\text{compute}}\right)

where $\mathit{BW}$ is memory bandwidth and $C$ is compute throughput. This is the roofline model, and the quantity that decides which term wins is arithmetic intensity — FLOPs performed per byte moved:

I = \frac{\text{FLOPs}}{\text{bytes}}, \qquad I_{\text{crit}} = \frac{C}{\mathit{BW}}

$I_{\text{crit}}$ is a property of the hardware alone, sometimes called its machine balance. An H200 delivers roughly 989 bf16 TFLOP/s against 4.8 TB/s of HBM3e bandwidth, so $I_{\text{crit}} \approx 206$ FLOP/byte. Any kernel doing fewer than 206 operations per byte it touches leaves the tensor cores idle waiting for memory. Most of what an LLM does during generation is nowhere close.

Prefill and decode are different machines

Inference splits into two phases with opposite bottlenecks, which is the single most important structural fact about serving.

Prefill processes the whole prompt at once. With $S$ prompt tokens, the model reads its weights once and does $S$ tokens' worth of arithmetic against them — so arithmetic intensity scales with $S$, and for any realistic prompt prefill is firmly compute-bound. It sets time-to-first-token (TTFT).

Decode generates one token per sequence per step. The model reads all of its active weights to produce a single token per sequence: a few dozen gigabytes moved to do a few gigaflops of work. Decode is violently memory-bound, and it sets time-per-output-token (TPOT), which is what a user experiences as speed.

These two phases want different hardware and different batching, which is why production stacks increasingly run them on separate GPU pools entirely — prefill/decode disaggregation. Everything that follows is about decode, because that is what "tokens per second" usually means.

What GLM-5.2 actually is

Before counting bytes, the architecture. GLM-5.2 is a sparse mixture-of-experts model with two features that change the arithmetic substantially — multi-head latent attention (MLA), borrowed from DeepSeek-V2, and DeepSeek Sparse Attention (DSA) with a cross-layer-shared indexer.

The ratio in the second row is the reason a 753B model is servable at all. Each token is routed to 8 of 256 experts per layer, so only about 40B parameters participate in producing it. Total parameters determine what you must store; active parameters determine what you must read. Those are different constraints against different hardware limits — capacity versus bandwidth — and conflating them is the most common error in back-of-envelope estimates.

Counting the bytes

For one decode step at batch size $B$ and context length $S$, three things cross the memory bus.

Weights. The batch-independent part — attention blocks, the 3 dense MLPs, the shared expert, routers, the unembedding — comes to 17.7B parameters. On top of that, every routed expert that any token in the batch selects must be read.

KV cache. Attention needs the keys and values of previous tokens. MLA does not store keys and values per head; it stores one compressed latent per token per layer, of dimension $d_c + d_{\text{rope}} = 512 + 64 = 576$. In bf16 that is

576 \times 2\ \text{bytes} \times 78\ \text{layers} = 87.75\ \text{KiB per token}

against 4.88 MiB per token for the same shapes stored as plain multi-head attention — a 57-fold reduction, and the entire reason a million-token context is tractable. DSA narrows the read further: the indexer picks the 2048 most relevant tokens per query, so attention reads 2048 tokens' latents regardless of whether the context is 8K or 1M.

Indexer state. The thing that picks those 2048 tokens has to look at all $S$ of them, reading a 128-dimensional index key per token. This is the cost that sparse attention adds back, and we will return to it.

Put those three terms together, divide by aggregate bandwidth, and you have a decode step. The figure below is that calculation, live:

Arithmetic intensity is 2.3 FLOP/byte against a machine balance of 206 — the tensor cores are idle 99% of the time. This is not a defect in the implementation. It is what generating one token at a time means.

Batching, and why it is not free for MoE

The standard fix for a memory-bound kernel is batching: read the weights once, amortise them over many tokens. For a dense model this works beautifully — weight traffic is constant in $B$, so intensity grows linearly and you march toward the compute roof.

For a mixture of experts it works much less well, for a reason that is easy to miss. Each token independently selects 8 experts. Two tokens will usually not select the same 8. As the batch grows, the union of experts the batch touches grows too, and so does the weight traffic. If routing were uniform and independent, the expected number of distinct experts touched in a layer is

\mathbb{E}[\text{experts}] = N\left(1 - \left(1 - \tfrac{k}{N}\right)^{B}\right)

with $N = 256$ and $k = 8$. Real routers are skewed — some experts are far more popular than others — which makes this an optimistic estimate. Skew means fewer distinct experts at a given batch size but worse load balance across GPUs under expert parallelism, so it moves the cost rather than removing it. That function saturates fast, and the consequence is stark:

Between batch 1 and batch 128, routed weight traffic rises about 32-fold. Per-token efficiency still improves — 40.3B parameters read per token becomes 5.7B — but nothing like the 128× a dense model would give you. And once every expert is being touched, extra batch genuinely is free, which is why MoE serving throughput curves have a distinct knee.

This is also why GLM-5.2 decode never becomes compute-bound. At batch 1024 the arithmetic intensity is still only 97 FLOP/byte, under the H200's 206. A dense model would have crossed into compute-bound territory around batch 200. The MoE stays on the memory roof, which means bandwidth, not FLOPs, is what you are buying when you buy GPUs to serve it.

Capacity: DRAM, and what the KV cache does to it

Bandwidth sets speed; capacity sets whether you can run at all. HBM — the stacked DRAM beside the GPU die — has to hold weights and KV cache simultaneously, and they compete.

GLM-5.2 in bf16 is 1403 GiB, which does not fit in eight H200s (1128 GB). In FP8 it is 753 GB and fits with about 375 GB to spare for KV. That headroom is the real constraint on concurrency, and at long context it disappears quickly: one million tokens of MLA cache is 87.75 GiB per sequence, so those 375 GB hold four such sequences.

Two things follow. First, quantisation buys capacity and bandwidth at once: FP8 halves both the bytes stored and the bytes read, which is why it is nearly universal in production and why NVFP4 is displacing it on Blackwell. Second, KV cache memory must be managed as a dynamic allocation problem, not a static reservation — the insight behind PagedAttention, which treats the cache as pages in a virtual memory system and recovers most of the waste that naive contiguous allocation causes.

SRAM, and why FlashAttention had to be invented

Everything so far has treated GPU memory as one thing. It is not. There is a hierarchy, and the gap between its levels is where a great deal of inference performance is won.

On an H100 or H200: HBM is ~80–141 GB at 3.35–4.8 TB/s. The L2 cache is 50 MB, considerably faster. Each of the 132 streaming multiprocessors has 228 KiB of configurable shared memory — SRAM, on the die, roughly an order of magnitude more bandwidth than HBM. Registers are faster still. The rule is the usual one: tiny and fast, or vast and slow.

Standard attention ignores this. It computes $QK^\top$, writes the resulting $S \times S$ score matrix to HBM, reads it back to apply softmax, writes it again, reads it once more to multiply by $V$. The score matrix is $O(S^2)$ and it makes several round trips over the slowest link in the system. At $S = 8192$, one head in one layer is a 134 MB matrix — already larger than the entire L2 cache, and 575 times larger than one SM's shared memory.

FlashAttention's observation was that attention is memory-bound, not compute-bound, and the fix is not fewer FLOPs but fewer bytes. It tiles the computation: load a block of queries and a block of keys into SRAM, compute their scores there, accumulate the softmax with a running normaliser so no full row is ever needed at once, and move on. The $S \times S$ matrix never exists in HBM. Only $Q$, $K$, $V$ and the output cross it. Same arithmetic, same numerics — exact attention, not an approximation — with asymptotically less memory traffic.

The subsequent versions are a case study in tracking hardware. FlashAttention-2 fixed work partitioning and parallelism. FlashAttention-3 exploited Hopper's asynchrony and FP8. FlashAttention-4 targets Blackwell, and its framing is instructive: Blackwell scales asymmetrically — tensor core throughput doubles while shared memory bandwidth and the special-function units that compute exponentials do not. So FA4 emulates $\exp$ with polynomials on the general-purpose FMA units rather than queueing for the SFU, and skips softmax rescaling unless numerical stability actually demands it. It reaches 1613 TFLOP/s on a B200, 71% of peak. When the bottleneck moves, the kernel has to move with it.

The cost FlashAttention does not remove

FlashAttention makes attention's memory cost linear. Its compute cost is still $O(S^2)$ — every query still scores against every key. At a million tokens that is unaffordable no matter how efficiently you move the bytes, and it is why GLM-5.2 uses sparse attention.

DSA puts a small "lightning indexer" in front of attention to pick the top 2048 keys per query, reducing core attention from $O(S^2)$ to $O(Sk)$. But the indexer must score all $S$ tokens to choose 2048 of them, so the indexer itself is $O(S^2)$ — and in the naive design it runs at every layer.

GLM-5.2's answer is that consecutive layers select nearly the same tokens, so most layers need not choose for themselves. A minority of "full" layers run an indexer; the rest reuse the nearest full layer's selection. This is visible in the checkpoint: only 22 of 79 layers carry indexer weights, a 72% reduction, which the model card reports as a 2.9× cut in per-token FLOPs at 1M context. Counted directly from model.safetensors.index.json: tensors named self_attn.indexer.* appear on 22 layers, and config.json's indexer_types array labels the rest shared. Independent measurements on a 30B DSA model report 1.82× prefill and 1.48× decode speedups from the same technique.

Speculative decoding: buying tokens with idle tensor cores

Return to the central embarrassment of decode: at batch 1, arithmetic intensity is 2.3 against a machine balance of 206. The tensor cores are almost entirely idle. Speculative decoding is the trick that spends them.

Draft $k$ tokens cheaply, then run the real model once over all $k+1$ positions in parallel and check which drafts it would have produced anyway. Accepted drafts are free tokens; rejected ones cost only the wasted draft. The verification pass is a prefill-shaped operation over $k+1$ tokens, and for a dense model it costs almost exactly what a single-token step costs — the weights get read once either way. Spare FLOPs become tokens.

For a sparse mixture of experts the story is more interesting, and it is the same story as batching. Those $k+1$ positions each route independently, so they drag in experts that were not being read. At batch 1 with $k=5$, the six positions touch about 44 experts per layer instead of 8, and the verification step costs roughly 3.5× a single-token step — enough to swallow the gain entirely. At batch 64 the server is already reading 222 of 256 experts, so those same six positions add almost nothing and verification really is nearly free.

So speculative decoding on an MoE is not uniformly cheap: it is cheap exactly where the expert weights are already saturated. One asymmetry does work in its favour throughout — the $k+1$ positions of a single sequence share one KV cache, read once and reused, whereas $k+1$ separate sequences would each need their own. Speculation buys tokens more cheaply than batching does, just not for free.

If each drafted token is accepted with probability $\alpha$, independently, the expected number of tokens emitted per verification step is

\mathbb{E}[\text{tokens}] = \frac{1 - \alpha^{k+1}}{1 - \alpha}

The $+1$ in the exponent is the bonus token the verifier produces even when every draft is rejected, which is why speculation can never be slower than not speculating, ignoring draft cost.

Where do drafts come from? GLM-5.2 ships a multi-token prediction head — a single extra transformer layer trained to predict the next token from the main model's hidden state, as in DeepSeek-V3. Because it shares the backbone's representations, its acceptance rate is high, and the model card reports GLM-5.2's MTP layer was improved specifically to increase accepted length by up to 20% over GLM-5.1. Serving stacks iterate the single head to draft several tokens: SGLang's low-latency preset for this model runs 5 speculative steps to produce 6 draft tokens.

From the roofline down to reality

Everything above is an upper bound. Real servers land below it, and the gap is worth understanding, because it is where engineering effort actually goes.

The roofline assumes you can saturate HBM. At batch 1 you cannot. The step is a chain of 78 layers, each a handful of small matrix multiplications whose operands must be gathered from scattered expert weights; kernel launch overheads and dependency stalls are a large fraction of the time. If the model is split across 8 GPUs by tensor parallelism, every layer needs a collective reduction — 78 layers, two synchronisations each, on the critical path of a step that is supposed to take a millisecond. Memory-bandwidth utilisation (MBU), the fraction of peak bandwidth actually achieved, is the number that captures all of this, and at batch 1 it is often well under 20%.

What to remember

Decode is memory-bound: throughput is bytes moved per step divided by bandwidth, and almost nothing else. For a mixture of experts, the bytes are the active parameters at batch 1 but creep toward the full parameter count as batching pulls in more experts, so per-user speed falls much faster than a dense model's would. The KV cache competes with the weights for capacity, and architecture choices like MLA change that budget by more than an order of magnitude. FlashAttention exists because the memory hierarchy is steep and the attention score matrix should never touch its slowest level; sparse attention exists because FlashAttention fixes the bytes but not the $O(S^2)$ arithmetic. Speculative decoding works because memory-bound decode leaves the tensor cores idle, and idle FLOPs can be spent guessing.

Do the arithmetic before believing a benchmark. It is only a division, and it will tell you within a factor of two what any configuration can possibly do — which is usually enough to know whether a reported number is impressive or merely unspecified.
